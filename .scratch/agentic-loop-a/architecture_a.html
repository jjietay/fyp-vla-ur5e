Architecture A: how it works now

Architecture A is a modular pipeline with nothing trained. A language model (Claude Sonnet 5.5) plans. An open-vocabulary detector (OWLv2) and a segmenter (SAM) see. Hand-written skills move the UR5e. On 26 Oct 2026 it became a loop: the planner makes one tool call per turn, perception is one of its tools, and code looks at the table after every skill.

Status. This design has 350 passing unit tests and an end-to-end test with fakes. It has not run on the arm yet. The last A that ran on the arm is tag a-pipeline-final (commit 4fe00b2). Section 17 lists what the bench must still confirm.

1. Overview

A spoken command becomes a transcript. The transcript goes to ArchitectureA.run(instruction), which returns an Outcome. Inside run, the planner and the code take turns:

Who decides

The LLM decides what to do next and which words to look for. It never sees pixels and never writes a pose.

Who checks

Code checks every call before it runs (validate_call), and the camera checks every pick and place after it runs.

Who remembers

The chat history holds the run's story. WorldState holds the facts about objects. Nothing carries over to the next instruction.

Who records

Trace writes one JSONL file per run, with one event per stage. That file is the evidence for H6 (A's failures can be traced to a stage).

2. One run, start to end

This is what happens for one spoken instruction, in the order the code does it. File and function names are given, so you can follow each step in the source.

  1. Startup, once per session (scripts/run_architecture_a.py). It loads faster-whisper large-v3 on CUDA in float16 first, because a missing PortAudio or a slow model load should fail before the arm is connected. Then it connects URController (RTDE to 10.149.230.1:30004), starts the RG2 gripper and opens the RealSense. It builds ArchitectureA one time. That constructor checks that the tool schemas match the Skills method signatures, reads T_base_cam from config/calibration/T_base_cam.json, and makes the Perception object. OWLv2 loads on the first detection and stays loaded for the whole process.
  2. Speech. You press Enter, speak, press Enter. SpeechToText.hear() gives the transcript exactly as heard: no cleanup, no lowercasing. The same string would go to B.
  3. Pre-run images. The script saves <run_id>_colour.png and <run_id>_depth.png to logs/traces/. This is outside the run, so it is not counted in A's time.
  4. New run objects. run() makes a new Trace (new run_id, new JSONL file), a new WorldState and a new Planner. Nothing from an earlier instruction survives in them.
  5. First planner call. planner.start(instruction) sends "Instruction: <transcript>" as the only message. The model writes a line of intent and calls perceive.
  6. Validate. _read checks that the reply has at most one call, that the first call is perceive, and runs validate_call. A refused call goes back to the model as an error and the model is asked again (section 9).
  7. Perceive. ArchitectureA.perceive writes a GROUNDING event with the planner's words, captures a frame (depth as a median of 5 frames), runs detection, SAM, the 3D localiser and the base-frame transform, and splits the result into "in reach" and "out of reach". WorldState.update matches the new objects to the known IDs. The result text plus "State now" goes back to the planner.
  8. Act. The planner calls one skill, for example pick(xyz). validate_call checks the envelope and that the xyz is within 50 mm of an object in view. ArchitectureA.act runs the skill, waits 0.3 s, captures one frame, checks the result with the camera (pick and place), and updates the state. The result (OK: or FAILED:) plus "State now" goes back.
  9. Operator verdict (optional, judge). After each skill, the bench operator types y/n. The answer goes into the trace and Outcome.judged only. The planner never sees it.
  10. Ask (if needed). If the planner calls ask_user, the question is printed, you answer by voice, and the transcript goes back as the tool result.
  11. Done. A reply with no tool call ends the run with ok=True and the model's sentence as the summary. If 12 model calls are used up, the run ends as "gave up", or as "plan rejected" if the last call was refused.
  12. Finish. trace.finish writes run_end with the total time and the first failed stage. The script prints the summary, the queries used, the calls run, the tokens and the trace path.

3. The LLM call

Every planner turn is one call to the Anthropic Messages API, made in Planner._turn (planner.py). The request has these parts:

client.messages.create(
    model="claude-sonnet-5-5",                 # config: architecture_a.planner.model
    max_tokens=2048,                           # config: architecture_a.planner.max_tokens
    system=SYSTEM_PROMPT.format(workspace=env.describe()),
    tools=TOOLS,                               # 7 tools, tools.py
    tool_choice={"type": "auto", "disable_parallel_tool_use": True},
    messages=self.messages,                    # the whole run so far, append-only
    extra_body={"thinking": {"type": "between_tools"},
                "output_config": {"effort": "high"}},
)
SettingValueWhy
modelclaude-sonnet-5-5Adopted 1 Oct 2026, when Sonnet 4.5 was deprecated. Grounding uses the same model, so no extra component enters A.
thinkingbetween_toolsSonnet 5.5 refuses disabled. between_tools is the lowest setting: no long reasoning before each answer, so the latency and the token counts stay comparable between runs.
efforthighbetween_tools is refused above high, so these two settings go together.
tool_choiceauto + disable_parallel_tool_useauto because forced tool/any is a 400 on Sonnet 5.5. disable_parallel_tool_use limits the model to one tool call per reply.
max_tokens2048Caps one reply. A reply is one intent line and one call, so this is far more than needed.
Turn limitmax_turns: 12Counts every model call in the run, rejected calls too. It is a safety property: it stops a model that keeps trying a failing grasp.
extra_bodythinking, output_configSent this way so that an older SDK forwards the fields and does not reject them. The lerobot venv has anthropic 1.11.0.
The API is stateless. The model remembers nothing between calls. Each call sends the full system prompt, all 7 tool definitions and the whole message list again. Everything the model "knows" in turn 5 is in that request.

Token use. Planner.usage adds input_tokens and output_tokens from every response, including rejected ones, and counts the calls. It goes onto Outcome.usage and is printed after each run. Prompt caching is not switched on.

4. The system prompt (in-context instructions)

A uses zero-shot prompting. There are no worked examples in the prompt. All of the model's behaviour comes from three places in the context:

1. System prompt

Rules for the whole run: perceive first, act only on positions in the state, ask rather than guess, one object in the gripper.

2. Tool descriptions

What each tool does and when to use it. The noun-phrase rules of ADR 0004 are in the perceive description.

3. Tool results

The facts of this run: OK/FAILED with the reason, and "State now" after every call.

This is the full system prompt, as the model receives it (the last line is filled in from the envelope in config.yaml):

You control a UR5e robot arm with a parallel gripper on a table.

Carry out the user's instruction by calling the tools available to you, one call per turn. Before each call, write one short line saying what you intend and why.

Rules:
- Your first call must be perceive. You see nothing until you look.
- Every result comes with "State now": the object in the gripper, the objects in view with an id and a position in the robot's base frame in metres, the objects no longer in view, and the objects seen but out of reach.
- Only act on positions taken from "objects" in the latest state. Never invent coordinates. Objects under "not_in_view" and "out_of_reach" have no position and must not be used. Call perceive again if what you need is not in view.
- Refer to objects by their id when you write or ask. Two objects with the same name are different objects. The skills take positions: copy the xyz of the object you mean from the latest state.
- perceive keeps only the best match for each name unless you raise max_per_query. Raise it when several objects may share a name.
- If the instruction names an object you cannot find, say so instead of substituting a similar one. Try perceive with other words first if the words you chose may be the reason.
- If an object the task needs is out of reach, do not move anything: tell the user it is out of reach and should be moved closer to the arm.
- The gripper holds one object at a time. Always place what you are holding before picking something else.
- If the instruction does not determine which object to act on, call ask_user. Do not guess and do not pick the first plausible candidate. After the answer, call perceive with the user's words if they name something you have not looked for.
- A result that starts with FAILED means the step did not work. Decide from the reason and the state whether to try again or to stop.
- Work in the order the task requires. If something must be open before you can put an object inside it, open it first.
- When the task is complete, stop calling tools and reply with one short sentence describing what you did.

Workspace limits: x[0.030,0.710] y[-0.700,0.030] z[0.181,0.380] radius[0.400,0.700] angle[-80,-25] deg, metres, base frame

Seven tools are in tools.py. Five are motion skills, carried out by Skills. perceive and ask_user are handled by the pipeline itself (NON_MOTION_TOOLS). The perceive description, in full

This text is where grounding now happens. The model reads it on every call.

Look at the table for the objects you name, and get back the state: what is in the gripper, each object in view with an id and a base-frame position, what is no longer in view, and what is seen but out of reach. Your first call must be this one. Call it again whenever you need different objects, for example after the user answers a question. Name objects as short noun phrases, lower case, no articles or verbs. Keep every distinguishing word the user said ('red cube', not 'cube') and add none they did not say. Include the destination as well as the object to move, and name a drawer by its handle ('drawer handle'). If the user names no specific object, name the categories the task implies ('a drink': 'bottle', 'glass', 'cup').

max_per_query: How many objects each phrase may find. Default 1, the best match only, which is right when there is one of each thing. Raise it when several objects may share a name and you need to see them all, for example two bottles. Each extra one is also a chance of a false detection, so keep it small.
Why noun phrases: OWLv2 turns each query into one CLIP text embedding and compares it with image patches. A whole sentence matches no region, and nothing in OWLv2 splits a sentence into its objects (ADR 0004).

What to notice

  • The state is inside the tool result, not in a separate message. A second result with the same tool_use_id is refused by the API (found on 1 Oct 2026).
  • Only the newest state matters, but older states stay in the history. The prompt says to act on the latest one. They are not summarised. A run is bounded by 12 calls, and one state of a few objects is a few hundred tokens, so a full run stays at a few thousand tokens of history.
  • Assistant content is appended whole (response.content): text blocks, tool_use blocks and any thinking blocks. That keeps the history valid for the next call.
  • The pick copies xyz from the state. The model never computes a position. Code then checks that this xyz is an object in view.

No long-term memory for the planner. A does not learn between instructions. It has no retrieval, no summary and no vector store. Each instruction starts cold, the same as B gets a new episode. For the FYP this is a good property: every trial is independent, so 20 trials are 20 samples.
Why two kinds of per-run memory. The conversation is the story: what the model intended, what each step said, what the user answered. It is free text, so code cannot check it. The WorldState is the facts: which ID is where, what is held. Code keeps it, so it is always correct by construction, and validate_call can check a pick against it. The model reads the facts, but it cannot write them.

8. The state and object IDs (state.py)

Data structures

@dataclass
class Tracked:              # one object A knows about
    id: str                 # "orange_1", "red_container_1"
    name: str               # latest query that found it
    confidence: float       # OWLv2 score from the latest sighting
    xyz: list[float]        # base frame, metres. Kept for matching, NOT shown when out of view
    last_seen: int          # planner turn of the latest sighting
    visible: bool           # seen in the latest look?
    looked_for: bool        # did the latest look search for its name?

class WorldState:
    tolerance: float        # verify.tolerance_mm / 1000 = 0.05 m
    objects: dict[str, Tracked]
    held: str | None        # ID in the gripper
    out_of_reach: list[dict]   # {name, confidence, reason}, no position
    _count: dict[str, int]  # next number for each base name

What the planner sees (render())

{
  "in_gripper": "orange_1",                         // ID only, no xyz
  "objects": [                                      // in view, can be acted on
    {"id": "red_container_1", "name": "red container", "confidence": 0.45, "xyz": [0.3207, -0.4809, 0.2216]}
  ],
  "not_in_view": [                                  // no xyz, ever
    {"id": "bottle_1", "name": "bottle", "last_seen_turn": 1, "why": "not looked for"}
  ],
  "out_of_reach": [                                 // no xyz, ever
    {"name": "white box", "confidence": 0.44, "reason": "position radius=0.849 is above max 0.700"}
  ]
}

How update() matches a new look to known IDs

  1. Remove the held object from the new rows. If something is held and the TCP position is known, the detection nearest the TCP within 50 mm is the held object, whatever query found it. It stays "in gripper". Without this, a look for "fruit" while holding orange_1 would offer fruit_1 at the gripper for a pick.
  2. Make every (new row, known object) pair within 50 mm, using all known objects except the held one, visible or not.
  3. Sort the pairs by distance, closest first. At equal distance, a pair with the same name comes first.
  4. Assign greedily, one to one. Take each pair in order unless its row or its ID is already used. Two bottles side by side cannot claim the same old ID.
  5. Matched: the known object takes the new name, confidence and xyz, and becomes visible with last_seen = this turn.
  6. Known but not matched: visible = false. why is "not looked for" if this look did not search for its name, otherwise "not seen".
  7. New rows not matched: each gets a new ID, the base name with spaces as underscores plus the next number: orange juice bottle → orange_juice_bottle_1.
  8. Out of reach is replaced with this look's list.
Why position and not name. After the user says "orange juice", the planner looks for "orange juice bottle". The bottle that answers is at the same place as bottle_2. A match by name would make a new ID, and the link between "the bottle I saw" and "the bottle the user means" would be lost.
Why no position for objects out of view. A stale position is a position the planner can act on. In Tier 3 a person moves things during the task. The xyz is still stored inside Tracked, so an object that comes back to the same place gets its old ID again. But it is never rendered, and target() ignores it.

  • target(xyz): the visible, not-held object nearest xyz within 50 mm, or None. validate_call uses it, and act uses it to name the object a pick aims at before the arm moves.
  • visible_xyz(): the positions a pick may aim at.

What happens on a refusal (ADR 0010). The whole reply is refused. Every tool_use in it gets a tool_result with is_error: true and REJECTED: <reason>. Correct this and try again. Then the model is asked again. The refusal counts as a turn. If the turn limit is reached while the last reply was refused, the run raises PlanRejected and ends as plan rejected: <reason> in the PLANNING stage. That is different from gave up after 12 planning turns, which means calls were accepted but the task was not finished.

Why place and the pour target are free. Putting something down on open table ("put it on the left") is a valid instruction. Only the targets that must be an object are tied to the state.

10. Perception (perception/)

One look is Perception.see(frame, queries, trace, strict, per_query) in scene.py. Every script that measures something also uses it, so a number from a script is the same number the pipeline acts on.

  1. Capture (CAPTURE stage). RealSense D435, fixed on its tape marks, about 0.74 m from the work area, about 45° down. Depth is the per-pixel median of 5 frames while the arm is at rest (noise only, not bias).
  2. Detect (DETECTION stage). OWLv2 google/owlv2-base-patch16-ensemble gets the colour frame and the planner's queries. It is loaded once per process, because loading it in each call cost 10.7 s per detection.
  3. Filter (filters.apply_filters). Score ≥ 0.3. Then NMS at IoU 0.5 across all queries, so two queries that box the same object keep only the better box. Then top_k_per_query keeps the k best boxes for each query, where k is the planner's max_per_query. The counts (raw, over threshold, after NMS, final) go into the trace.
  4. Localise (DEPTH stage), method mask_ray. SAM (facebook/sam-vit-base) makes a mask from each box. The mask outline is eroded by 3 px, where the table blends in. Depth gives only the object's height: the 95th and 5th percentile of the mask's base-frame z. The ray through the mask centre is cut at the object's centre height above the known table (table_z 0.176 m). If fewer than 30 depth points remain, the height comes from the mask's pixel size.
  5. Transform (TRANSFORM stage). Camera point to base frame with T_base_cam. A centre a little below the floor (up to 40 mm) is lifted to the floor, because that is the centre push going through an open box's floor. Objects with no valid depth are dropped, never sent with a null position.
  6. Reach split. in_reach: inside the horizontal ring sector and not under the floor. The z ceiling is not applied here, because a held orange reads above it. out_of_reach: name, confidence and the envelope's reason, no position.

Strict and not strict. When the planner calls perceive, see runs in strict mode with the trace. A stage that finds nothing raises inside its own trace stage, so the trace blames that stage. The pipeline catches the error and returns FAILED: ... to the planner, and the planner can try again. The look after a skill runs without a trace and not strict. An object hidden by the gripper is expected there, and it must not be counted as a detection failure.

Calibration (ADR 0007, no markers). T_base_cam is fitted each session with a ball (an orange) in the gripper on a grid of poses (calibrate_ball.py). Then level_to_table.py corrects height and tilt against the table. A reach test (check_calibration.py) is the only thing that can mark it validated. On 21 Oct: RMS 7.3 mm over 39 poses, plus an empirical reach_correction step.

11. Skills and the check after each (skills.py, pipeline.act)

The skills

SkillWhat it does
pick(xyz)Computes the grasp point 28 mm below the centre (grasp_depth_offset), but never under the floor. Checks all three poses (above at +0.12 m, grasp, retreat at +0.15 m or the ceiling) against the envelope before the first motion. Opens, moves above, moves down, closes and reads the width. Under 5 mm means nothing is held. Lifts, then closes again: if the fingers now close under 5 mm, the object dropped during the lift (13 Oct: five picks reported a hold and lifted nothing).
place(xyz)Drop point = xyz + release_clearance (default 0.01 m). Checks all poses first (13 Oct: a retreat found out of bounds after the gripper opened). Moves above, moves down, opens, retreats.
pourPicks the source, moves above the target, tilts in 12 steps up to tilt_rad (default 1.9), holds, returns it. Not used in Tier 0.
open_drawerGrasps the handle and pulls. pull_axis is a placeholder and WILL misbehave
homeJoint move to robot.home_q, after check_joint_move refuses any joint step over 30°.

Poses use the UR format [x, y, z, rx, ry, rz] in base frame. The tool points down with a fixed rotation vector (down_rotvec). Skills use only the shared controller API: move_to_pose, move_joints, gripper_toggle, get_state.

The look and check after every skill

Inside the EXECUTION stage, act does this:

  1. For a pick, find the target ID with state.target(xyz) before the arm moves, while the object is still where the planner saw it.
  2. Run the skill.
  3. Wait settle_s (0.3 s), capture one frame, run see with the latest queries and max_per_query, and read the TCP from RTDE.
  4. If the skill reported OK and it is a pick or place, run _check (table below). For other skills that reported OK, add "unverified: no check exists for <tool>".
  5. Update the state from this look, with the TCP so the held object is recognised.
  6. If the look itself failed: believe the finger width (held after pick, empty after place), mark everything out of view, and add "the look after the step failed".
SkillCamera seesResultState

picktarget's name, but further than 50 mm from the TCPFAILED orange_1 is not at the gripper after the pick: seen at … The width said held: …not held; object stays on the table

The check uses the raw located points (Seen.located), not in_reach, because a held object can be above the z ceiling. The 50 mm limit covers the 12–34 mm calibration error and the centre sitting about 2 cm above the fingertips.

Operator verdict. After the EXECUTION stage closes (so the wait is not counted as A's time), judge asks the operator "pick {'xyz': [...]}". The question shows only the step, not A's own verdict, so the two verdicts stay independent. The answer goes into a verdict record in the trace and into Outcome.judged. It never reaches the planner: an operator who says "that pick failed" would be a perfect sensor that B does not have.

17. Not yet verified, and known limits

Nothing in this page has run on the arm. Before T2, one spoken Tier 0 command must confirm these points in the trace:
  • The API accepts disable_parallel_tool_use with between_tools on our key. The docs say yes. Our account has not sent it yet.
  • The model writes an intent line and calls perceive first, without needing a refusal.
  • One call per turn in practice; the token count per run compared with the old A.
  • The check names the object by ID (verified: orange_1 …).
  • Latency: one capture per skill now, and a perceive turn adds one model call.

Known limits:

  • max_per_query above 1 is untested on real frames. A second box can be a false detection. Check this before the Tier 2 trials.
  • An unverified place counts as OK. After the fingers open they cannot hide the object, so "not seen" may need to become FAILED. You decided to keep it for now.
  • No check exists for pour, open_drawer or home. The look still updates the state.
  • The place check asks only "is it away from the gripper". It does not test "fully inside the container", which is the Tier 0 success rule.
  • outcome.ok is True on a refusal such as "the box is out of reach". Harmless while success is the operator's y/N.
  • The planner does not see the image. With two bottles it can tell them apart only by position and words. Giving it the image would change what A is, and that needs its own ADR.
  • Trials before 26 Oct 2026 cannot be compared with trials after it (ADR 0012).
